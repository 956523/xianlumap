## 【问题 1】全屏时剖面叠在线路上 —— ✅ 已修复

**根因**：`#map` 是 `height: 100vh`，地图把整个视口铺满并以**视口中心为基准居中路线**；
抽屉展开后盖住下半屏，但地图**不知道**自己被遮挡了 → 路线相对可见区偏下、被压住。

**修法**（地图软件标准做法：**改容器，不是改内容**）：

```css
#map { height: calc(100vh - var(--elev-occupy, 0px)); }
```

抽屉开合/拖拽时同步 `--elev-occupy`，地图容器主动让位 → 地图中心永远是**真正可见区域**的中心。

| 状态 | `--elev-occupy` | 地图高（1080 视口） |
| ---- | ---- | ---- |
| 收起 | 46px | 1034 |
| 展开 | 258px | **822** |

配套三件事：
1. **`ResizeObserver` 监听地图容器** → 尺寸变化通知地图引擎 `resize()`，并防抖后重算全览视角
2. **`fitAll` 的 zoom 改为自适应容器高度**（全屏时看得更全，矮容器适当拉近），不再写死 `6.2`
3. 拖拽中给地图容器加 `transition: none`，保证跟手不迟滞

## 【问题 2】天数、地点写死，不支持编辑 —— 需要做的改造

### 现状：数据全部内联在 HTML 里，共 7 处硬编码

| 数据 | 位置 | 规模 | 问题 |
| ---- | ---- | ---- | ---- |
| 真实高程序列 | `ALT_REAL` | 661 点 | 构建产物，不该手改，但可以改采样源 |
| 地名标注 | `ALT_MARKS` | 27 条 | **地名要能改**（比如这次不去野牛沟） |
| 每日行程 | `CORE` / `TAIL` | 4 段 + 1 段 | **天数要能改**（拆天、并天、加休整日） |
| 每日元信息 | `DAY_META` | 11 条 | 每天标题/备注/缩放级别 |
| 站点数据 | `STATION_DATA` | 300 条 | 构建产物 |
| 起点坐标 | `P_LZ_XN` / `LZ_HEAD` | — | 换起点城市要改 |

### 方案：三层数据模型 + 参数化入口

把「**引擎（不变）**」和「**路线定义（可编辑）**」彻底分离：

```
┌─────────────────────────────────────────┐
│ Layer 1 · 路线定义（用户可编辑）          │  ← 一个 JSON，可导入导出
│   - 途经点列表（名称 + 坐标 + 是否垭口）   │
│   - 分段方案（哪天到哪、住哪）             │
│   - 出发地选项                            │
└─────────────────────────────────────────┘
                  ↓ 构建脚本消费
┌─────────────────────────────────────────┐
│ Layer 2 · 固化产物（构建生成，不手改）     │  ← route-real-data.js / stations-data.js
│   - 真实轨迹（腾讯驾驶 API）               │
│   - 真实高程（open-meteo）                 │
│   - 沿线站点                                │
└─────────────────────────────────────────┘
                  ↓ 页面运行时消费
┌─────────────────────────────────────────┐
│ Layer 3 · 渲染引擎（通用，与路线无关）     │  ← 页面 JS，可复用到任何线路
│   - 地图绘制 / 剖面绘制 / 续航规划          │
└─────────────────────────────────────────┘
```

**具体改造**：

| 改造项 | 做法 |
| ---- | ---- |
| **数据外置** | 把 Layer 1 抽成 `route-def.json`：`{ meta, waypoints:[], days:[], starts:[] }` |
| **页面不再内联** | 页面通过 `<script src="route-def.js">` 引入（`route-def.json` 的 JS 包装，避免 file:// 的 fetch 限制） |
| **改天数** | 编辑 `days[]`：调 `from`/`to` 途经点 + 标题。构建脚本据此重新切里程区间，**不需要重新拉腾讯 API**（轨迹没变） |
| **改地点** | 编辑 `waypoints[]`：加/删/改名字。**改名字是纯前端改（立刻生效）；加删坐标点需要重跑构建**（要重新拉轨迹） |
| **页面内编辑（可选）** | 提供一个编辑模式面板：改每日标题/备注直接存 localStorage，支持导出 JSON。**零构建即可改文案** |

**关键设计判断**：区分「**改文案**」和「**改几何**」——
- 改文案（天标题、地名显示、备注）→ 页面内直接编辑，即时生效
- 改几何（加删途经点、换路线）→ 必须重跑构建脚本（因为要拉真实轨迹和高程）

这个区分很重要：它决定了这个页面是能用 Excel 精神改的，还是必须找开发者改的。

2. 现有 `STATION_DATA` 的 180 条记录字段是 `t/a/tel/lat/lng/km/d`，同样没有
3. 枪数属于**运营商自有数据**（特来电/星星充电/国家电网/云快充各自旗下），腾讯只做聚合展示，不通过开放 API 输出
4. （当天该 key 额度也用完了：`status 121 此key每日调用量已达到上限`）

**可选路径（需你选）**：

| 方案 | 数据来源 | 可行性 | 代价 |
| ---- | ---- | ---- | ---- |
| **A. 手动标注关键站** | 人工/半自动查运营商 App | ✅ 高 | 只标关键补给站（如 20-30 个），而非全部 180 个 |
| **B. 接入运营商开放 API** | 特来电/星星充电开放平台 | ⚠️ 中 | 需注册开发者、多数要企业认证 |

- **快充/慢充**（决定要不要等 2 小时）
- **运营商**（决定要装几个 App）

## 【问题 3】路线显示抽象出来，支持其他线路 —— 这个方向对，但要注意边界

**你的直觉是准的。** 现在这个页面里，真正**通用**的部分比你想的多：

| 模块 | 通用性 | 说明 |
| ---- | ---- | ---- |
| 地图容器 / 图层开关 / 抽屉交互 | ✅ **完全通用** | 与路线无关 |
| 海拔剖面绘制（含 Y 轴自适应、标签避让） | ✅ **完全通用** | 只吃 `[{km, alt, n}]` |
| 续航贪心规划算法 | ✅ **完全通用** | 只吃站点里程 + 车续航 |
| 按天切片 / sparkline | ✅ **通用** | 只吃每日里程区间 |
| 腾讯驾车路线拉取 + 解码 | ✅ **通用** | 只吃起终点对 |
| open-meteo 高程采样 | ✅ **通用** | 只吃坐标序列 |
| **青甘线的具体地名/垭口/每日安排** | ❌ **不通用** | 这就是 Layer 1 |

**结论**：**约 85% 的代码本来就是通用的**，只是现在和青甘线的数据搅在一起。

### 抽象方案

做成**路线引擎 + 路线包**的形式：

```
route-engine.html        ← 引擎（通用，不含任何青甘线内容）
route-defs/
  qinghai-gansu.js       ← 青甘线定义（Layer 1）
  sichuan-west.js        ← 川西线定义（示例：只需写这个文件）
  xinjiang-north.js      ← 北疆线定义
```

**页面启动时**：读 URL 参数或下拉选择 → 加载对应 `route-def` → 运行引擎。
**构建脚本**：`build-route.js <route-def.json>` → 产出对应固化数据。

### ⚠️ 边界与风险（这个必须先说清楚）

1. **抽象是有成本的**。现在硬编码虽然难看，但它**零抽象开销**。抽象后要处理不同线路的结构差异——
   比如青甘线是**环线**，川西可能是**往返线**，北疆可能是**多分支**。过度抽象会做出一套谁都用不顺的框架。

2. **我建议的抽象粒度**：**不做任意线路通用，做同类型环线/单线通用**。
   即支持一串有序途经点 + 分段方案这种结构，**不**去支持多分支、跨天自由组合。
   青甘、川西、北疆、甘南、独库——这几条都符合有序途经点结构，覆盖你 90% 的可能需求。

3. **不引入构建复杂度**。不搞 webpack/vite，保持改文件刷新页面的单文件精神。
   `route-def.js` 就是个 JS 对象字面量，跟现在 `stations-data.js` 一样。

4. **数据量问题**。现在 661 高程点 + 2660 轨迹点已经 196KB。多条线路如果全塞一个页面会很大。
   → 按需加载：选了哪条线才加载哪条的数据。

### 实施顺序建议

| 阶段 | 内容 | 产出 |
| ---- | ---- | ---- |
| **P1** | 数据外置：`ALT_MARKS` / `DAY_META` / `CORE` / `TAIL` 抽成 `route-def.js` | 青甘线行为不变，但数据可改 |
| **P2** | 页面内编辑模式（改文案，存 localStorage + 导出 JSON） | 你能直接改天标题/地名 |
| **P3** | 引擎与数据分离：`route-engine.html` 消掉所有青甘线硬编码 | 骨架通用 |
| **P4** | 加第二条线验证抽象（建议川西小环线，结构最接近） | 证明真的能复用 |
| **P5** | 充电枪数（方案 A+D） | 关键段准确 |

**P4 是关键**：只有真的跑通第二条线，才证明抽象是对的。**不做 P4 的抽象都是纸上谈兵。**

### v8 交互重构 + 层级 bug 修复（开洋指出：剖面点击不展开；建议参考地图软件抽屉交互）

**① 根因：z-index 被地图覆盖层反超（我上一版引入的 bug）**

腾讯地图 GL JS 会在 `#map` 内部插入一个 **`z-index: 1000`** 的覆盖层容器：

| 元素 | 修复前 z-index | 命中测试结果 |
| ---- | ---- | ---- |
| `#map` 内部覆盖层（腾讯） | **1000** | — |
| `#elev` 剖面面板（我写的） | **998** ❌ | `elementFromPoint` 返回地图 div |
| `#panel` 侧栏 | 1000 ⚠️ | 同级，靠 DOM 顺序侥幸可用 |

→ 剖面面板**看得见、点不动**，因为鼠标事件被地图图层吃掉了。

**为什么之前没发现**：所有验证都用 `element.click()`（程序化触发，**绕过命中测试**）。这次改用 `mousemove + mousedown/mouseup` 真实鼠标事件，立刻暴露。

**修复**：建立统一层级变量体系，全部 UI > 1000：

```
--z-map-overlay: 1000   /* 腾讯地图内部覆盖层（外部约定值，勿动） */
--z-panel:       1100   /* 侧栏 */
--z-drawer:      1200   /* 底部抽屉 */
--z-collapse:    1250   /* 侧栏展开把手（须在抽屉之上） */
--z-tip:         1300   /* 悬浮提示 */
```

并在代码顶部写了注释警告，防止以后再踩。

**② 交互重构为地图软件惯例**

| 原交互 | 新交互 |
| ---- | ---- |
| 剖面是"折叠面板"，点标题开合 | **可拖拽底部抽屉**：拖手柄调高度、下拖到底自动收起、点击手柄/标题开合 |
| 高度档位按钮（紧凑/标准/加高） | 删除——拖拽本身就是连续调节 |
| 侧栏与剖面互相挤，需要写一堆避让计算 | 抽屉**独立浮在侧栏之上**（地图软件惯例），避让逻辑全部删除 |
| 侧栏收起只在窄屏（≤720px）可用，且靠外部悬浮按钮 | **全尺寸可折叠**：面板自带 `‹` 折叠按钮 → 滑出 → 左上角 `☰ 行程` 把手展开 |
| `#evbar` 电车提示用 `bottom: 78px` 魔法数字悬浮在页面中部 | 并入抽屉信息栏作为**可关闭通知项**（`#evNotice`），不再撞抽屉 |
