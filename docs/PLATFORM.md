## 0. 先说清楚：这件事难在哪

从"一条线"到"所有线"，90% 的人会做成一件事：**写一个配置很全的框架，最后谁都用不顺**。

我不想干这个。所以先把最难的三件事摊开：

### 难题一：抽象粒度 —— 不是"支持多少条线"，是"引擎吃什么、吐什么"

上一轮我犯过的错：把"只支持有序途经点"写成需求边界。
**那是实现结论，不是需求边界。** 需求边界应该是**输入的形状**。

我的判断：**输入的形状 = 一条有序的折线 + 一个分段方案。**

| 线路类型 | 能不能吃下 | 为什么 |
| ---- | ---- | ---- |
| 环线（青甘、川西小环线） | ✅ | 有序点，首尾相接 |
| 单线/往返线（318、独库） | ✅ | 有序点，不闭合 |
| 多分支（主线+支线，如青甘的拉脊山支线） | ✅ | **一份主折线 + N 条可选支线**，支线不进主里程 |
| 跨天自由组合（同一条路拆几天走） | ✅ | 分段方案是**在主折线上的区间** |
| 网格状路网（"我想随便走"） | ❌ | 没有"主折线"这个概念，硬塞会做出四不像 |

**结论**：支持"**主折线 + 分段 + 支线**"，不支持任意路网。这覆盖了自驾攻略型线路的绝大多数。

### 难题二：数据从哪来 —— 这是真正的瓶颈，不是架构

平台化之后，**每加一条线，就要能自动把它的数据搞到手**。现在青甘线的数据是怎么来的：

| 数据 | 来源 | 能不能自动化 |
| ---- | ---- | ---- |
| 真实轨迹 | 腾讯驾车路线 API（起终点对） | ✅ 全自动 |
| 真实高程 | open-meteo Elevation（50 点/批） | ✅ 全自动 |
| 沿线站点 | 腾讯 POI `region()` 穷举 | ⚠️ **半自动** —— 要人工列行政区 |
| 途经点/地名 | **我手打的** | ❌ **纯人工** |
| 分段方案（几天、住哪） | **我手打的** | ❌ **纯人工** |
| 海拔标注点的名字 | **我手打的** | ❌ **纯人工** |

**这张表的第 4、5、6 行，就是平台化的真正成本。**

一个方案要点 20–30 个途经点、分 8–12 天、标 20 多个地名。
如果每加一条线都要我手打一遍，那不是平台，那是**我当人工标注器** —— 就是你上次骂的那个"你拿我当日本人整"。

**所以平台化必须回答：怎么让"加一条线"变得不需要我。** 三个可能的路子（§3 详述）：
1. **线路包只写途经点**，地名/分段从途经点自动推导（+ 用户页面内改）
2. **从公开攻略帖抓线路**（马蜂窝/小红书）—— 有合规风险，且结构化难
3. **让用户自己填**（页面内有编辑模式，导出成线路包）

我倾向 **1 为主 + 3 兜底**。

### 难题三：站点数据在腾讯这条路上是"有天花板"的

上一轮已经测穿：`boundary=region(行政名,0)` 是腾讯代理唯一能用的边界，**只覆盖建成区**。
大柴旦能抓到 27 个站，靠的是我人工把它列进 `REGIONS`。**戈壁走廊永远抓不全。**

这意味着：
- 青甘线的"199.9km 无桩"是**接口上限**，不是抓漏
- 换一条线（比如 318 川藏线），无人区段会更长，问题更严重
- **平台化不会解决这个**，只会让它暴露得更频繁

**必须给用户一个"数据可信度"的表达方式**（§5.4），而不是假装数据是全的。

## 1. 产品定位

### 一句话

> **给自驾攻略型线路，做一张"打开就能用"的规划地图** —— 路线、补给、海拔、续航，一屏看全，零操作成本。

### 用户是谁

自驾出发前**查攻略、排行程**的人。典型动作：
1. 我这条线多少公里、几天能走完
2. 哪段最险（海拔、无补给）
3. 我的车（电车/油车）续航够不够，在哪充/加油
4. 每天开多少、住哪

### 不是谁

- 不是导航工具（不做实时路况、不做语音导航）
- 不是轨迹记录（不做 GPX 导入导出为主功能）
- 不是攻略社区（不做 UGC 内容）

### 与导航 App 的边界

| 导航 App 能做 | 这个产品做 |
| ---- | ---- |
| 实时路况、逐向导航 | **出发前**的全线地形/补给/续航体检 |
| 你告诉它去哪，它给一条路 | 你告诉它"我想走这条线"，它给出**这条线的全部代价** |

**边界的关键**：这是一张**有观点的图**（"这段别逞能，充到 100% 再走"），不是一张客观的图。

## 2. 需求边界（抽象颗粒度）

### 2.1 引擎必须吃到的东西（线路包契约）

一条线路 = **一个 JS 对象**（`route-<id>.js`），字段如下：

```javascript
{
  id: 'qinghai-gansu',
  meta: {
    name: '青甘大环线',
    region: '青海 · 甘肃',
    updatedAt: '2026-09-26',
    // 数据可信度声明（见 §5.4），平台必须透出而不是藏起来
    caveat: '站点覆盖以行政区建成区为准，戈壁无人区可能存在未收录桩点'
  },

  // ① 主折线：途经点（有序）。这是引擎的输入核心
  waypoints: [
    { n: '西宁',   p: [36.6171, 101.7782], type: 'start' },
    { n: '二郎剑', p: [36.5820, 100.4880], type: 'via' },
    …
    { n: '西宁',   p: [36.6171, 101.7782], type: 'end' }   // 环线 = 首尾同点
  ],

  // ② 支线（可选，不进主里程）
  branches: [
    { n: '经典线·翻拉脊山', from: '西宁', to: '倒淌河',
      avoidHighway: true, note: '拉脊山垭口 3820m，主线路过而不翻' }
  ],

  // ③ 分段方案：主折线上的区间切分（改天数只改这里）
  days: [
    { id: 1, from: '西宁', to: '二郎剑', title: '西宁 → 青海湖二郎剑',
      note: '京藏高速 · 倒淌河 · 初见青海湖', stay: '二郎剑' },
    { id: 6, rest: true, title: '敦煌休整', note: '鸣沙山 · 莫高窟（需提前预约）' },
    …
  ],

  // ④ 地名标注（海拔剖面用）。n 必填，其余可自动补齐
  marks: [
    { n: '日月山垭口', p: [36.4440, 100.8000], pass: true },
    { n: '德令哈',     p: [37.3740, 97.3710] }
  ],

  // ⑤ 出发地（同一线路多起点的差异）
  starts: [
    { id: 'xn', name: '西宁', p: [36.6171, 101.7782] },
    { id: 'lz', name: '兰州', p: [36.0611, 103.8343] }
  ]
}
```

**注意 ③**：`days` 的 `from`/`to` 引用**途经点的名字**，不写坐标、不写里程。
里程由构建脚本算。这样改天数只是改名字，**同时点名的途经点自动落进对应天**。

### 2.2 构建管线吐出的东西（固化产物）

```
route-<id>.data.js   ← 构建产出，页面引入
{
  builtAt, totalKm,
  legs:     [{ id, name, apiKm, roads, path:[[lat,lng],…], elev:[[km,alt],…] }],
  stations: { ev: [...], fuel: [...], coverage: { maxGapEv, maxGapFuel, blind: [...] } },
  warnings: [{ level:'warn', km:[1000,1175], msg:'199.9km 无桩（真实无人区）' }]
}
```

**关键约束（沿用已验证的结论）**：
- `path` 必须来自**真实驾车轨迹**，不能手打（手打折线 ±10km 误差，已踩过）
- `elev` 必须来自**真实地形采样**，且要做中值滤波去尖峰（已踩过 2 处）
- 站点 `km` 必须用**同一条 path 投影**，否则站名和位置错配（已踩过）
- 规划/统计用**全量站点**，地图打点用**屏幕去重后**的 —— 两口径不能混（已踩过）

### 2.3 引擎绝对不管的事（边界，防过度抽象）

- ❌ 不管"这条线值不值得去"
- ❌ 不管实时路况/天气
- ❌ 不管路网路径规划（只消费已有折线，不自己算路线）
- ❌ 不管多线路拼接（"青甘+川西连起来走 20 天"——那是另一个产品）
- ❌ 不做在线编辑协作

## 3. "加一条线"的完整流程（平台化的核心问题）

### 3.1 现状 vs 目标

| 步骤 | 现在（青甘线） | 目标 |
| ---- | ---- | ---- |
| 列途经点 | 我手打 26 个 | **我手打 20 个**（无解，必须有人决定走哪） |
| 拉轨迹 | 跑脚本 | 跑脚本 ✅ |
| 采高程 | 跑脚本 | 跑脚本 ✅ |
| 标地名 | 我手打 27 个 | **自动取途经点 + 用户页面内改** ⬅ 关键改进 |
| 分天数 | 我手打 10 天 | **自动按日均 250km 初分 + 用户页面内改** ⬅ 关键改进 |
| 抓站点 | 我手列 63 个行政区 | **半自动**：按折线包围盒推出候选行政区，我确认一遍 |
| 写文案 | 我手打 | **模板生成骨架 + 用户改** |

**能看到的关键改进**：把"手打 27 个地名 + 手打 10 天分段"这两件事，变成**自动初稿 + 用户微调**。

### 3.2 分工原则（这条是底线）

> **几何必须由人定，文案必须由人改，中间的一切由脚本算。**

- **人定**：走哪条路（途经点）—— 这是产品判断，脚本给不出来
- **脚本算**：里程、海拔、坡度、站点、缺口、续航规划
- **人改**：天怎么分、名字怎么叫、备注写什么 —— 在页面里直接改，存 localStorage，导出成新线路包

### 3.3 页面内编辑模式（必做，优先级高）

这是把"平台"从"我帮你做"变成"你自己能做"的开关。

| 能改 | 存在哪 | 生效方式 |
| ---- | ---- | ---- |
| 天标题 / 备注 / 住宿点 | localStorage | 即时 |
| 天数的 from/to（拖动切分点） | localStorage | 即时（重新切里程区间） |
| 地名显示名 | localStorage | 即时 |
| 途经点增删 | — | **需重跑构建**（要拉新轨迹） |
| 导出 | 下载 `route-<id>.custom.json` | 可分享/归档 |

**判断依据**（沿用 PROJECT.md 的区分）：**改文案 = 页面内即时；改几何 = 必须重跑构建。**

## 4. 分层架构

### 4.1 三层，职责不重叠

```
┌─────────────────────────────────────────────────────────┐
│  L1 · 线路包（数据层）                                    │
│  route-defs/qinghai-gansu.js    ← 人写：途经点/分段/地名   │
│  route-defs/qinghai-gansu.data.js ← 脚本产：轨迹/高程/站点 │
│  ─────────────────────────────────────────────────────   │
│  新增一条线路 = 新增两个文件，引擎零改动                    │
└─────────────────────────────────────────────────────────┘
                          ↓ 被 L2 消费
┌─────────────────────────────────────────────────────────┐
│  L2 · 引擎（应用层）                                      │
│  engine/route-engine.js   ← 地图/取景/图层/缩放分级        │
│  engine/profile.js        ← 海拔剖面（含 Y 轴自适/避让）   │
│  engine/planner.js        ← 续航规划（贪心 + 30% 红线）    │
│  engine/ui.js             ← 侧栏/抽屉/图层开关/编辑模式    │
│  ─────────────────────────────────────────────────────   │
│  零业务硬编码：不含任何地名、里程、站点                    │
└─────────────────────────────────────────────────────────┘
                          ↓ 被 L3 驱动
┌─────────────────────────────────────────────────────────┐
│  L3 · 构建管线（工具层，Node 跑）                          │
│  tools/build-route.js     ← 途经点 → 真实轨迹 + 高程       │
│  tools/build-stations.js  ← 折线 → 沿线站点 + 覆盖体检     │
│  tools/validate.js        ← 线路包体检（见 §5）            │
└─────────────────────────────────────────────────────────┘
```

### 4.2 现有 1650 行的拆分归属

| 现有模块 | 行数（约） | 归属 | 说明 |
| ---- | ---- | ---- | ---- |
| `ALT_REAL` / `ALT_MARKS` / `CORE` / `TAIL` / `CLASSIC` | 190 | **L1** | 抽成线路包 |
| `CITIES` / `SPOTS` / `FUELS` / `EVS` | 75 | **L1** | 同上 |
| `STATION_DATA` | 1（但 76KB） | **L1** | 移到 `.data.js` 外置 |
| `P_LZ_XN` / `LZ_XN_KM` / `TOTAL_XN` | 5 | **L1** | 出发地差异，进 `starts[]` |
| `visibleBox` / `zoomToFit` / `fitAll` | 90 | **L2** | ✅ 已经通用，直接搬 |
| `dedupeByScreen` / `stationsAll` / `activeStations` | 60 | **L2** | ✅ 已经通用 |
| `planCharging` / `renderPlanPanel` | 120 | **L2** | ✅ 已经通用（但混了青甘的文案） |
| `drawProfile` / 抽屉拖拽 / 图层体系 | 300 | **L2** | ✅ 已经通用 |
| `buildDays` | 25 | **L2** | ⚠️ 含青甘专属分支，要改为读 `days[]` |
| 其余（初始化/信息窗/图标/渲染） | 800 | **L2** | 大部分通用 |

**结论：约 1300 行（79%）本来就是通用的**，只是和 350 行青甘数据搅在一起。

### 4.3 不引入构建工具链

**保持单文件精神**：不用 webpack/vite/TS，`route-defs/*.js` 就是一个 JS 对象字面量（和现在的 `stations-data.js` 一样）。
理由是验证过的：**改文件刷页面就能看**，这个回路短得值钱。

但必须做**按需加载**：1660 个轨迹点 + 661 个高程点 + 475 个站点已经 195KB，
多条线路不能全塞一个页面 → 选哪条线才加载哪条的数据。

## 5. 数据可信度（这一节是新增的，很重要）

平台化后，用户会拿这个图去**没去过的地方**做判断。
**说错话的代价比现在大得多。** 所以要有一套"数据体检"机制。

### 5.1 四类体检，构建时跑，结果固化进页面

> **2026-09-28 已落地**：`tools/validate.js <线路包> [--fix]` 实现下表 V1–V4，
> 实测记录见 EXECUTION.md §10（青甘 V4 抓出 281km 陈旧常量并修正）。

| # | 体检项 | 判据 | 不通过怎么办 |
| ---- | ---- | ---- | ---- |
| V1 | **物理合理性** | 相邻点坡度 > 120 m/km（正常山路 40–80） | 中值滤波修 + 页面标注 |
| V2 | **补给覆盖** | 25km 网格有无站点；长盲区 > 100km | **页面显式标出"无桩段"**，不藏 |
| V3 | **投影自洽** | 站点投影 km 与该点最近途经点的里程差 | 超阈值报警（说明轨迹与站点对不上） |
| V4 | **里程对账** | 逐日累加 vs 折线总长 vs 站点表 totalKm | 三者必须一致（已踩过：常量陈旧差 281km，S4 已修）|

### 5.2 "数据可信度"要透出给用户

不是藏在文档里，是**画在图上**：

| 表达 | 位置 | 例子 |
| ---- | ---- | ---- |
| 地图上标出长盲区段 | 折线染色 + 文字 | "km1000–1175 无桩（199.9km）" |
| 每个站点带来源日期 | 信息窗 | "腾讯 POI · 2026-09-26" |
| 侧面声明 | 侧栏底部 | "站点为整理时点快照，出行前请用地图 App 复核" |

### 5.3 一条硬规矩

> **抓不到的，不许假装抓到了。**

腾讯这条路抓不全戈壁，就在页面上写清楚"这一段以建成区为准"。
**不做"人工补齐数据"** —— 那是造假，而且是你上次明确骂过的方向。

## 6. 验证方法：怎么证明"真的能服务所有线路"

### 6.1 做第二条线（唯一有效的证明）

**不做第二条线的抽象，都是纸上谈兵。**

选线标准：
- 结构不同（证明抽象不是给青甘量身定做的）
- 数据能自动拿到（否则卡在难题二）

| 候选 | 结构 | 与青甘的差异 | 数据可得性 |
| ---- | ---- | ---- | ---- |
| **川西小环线** | 环线 | 短（约 900km）、无戈壁、桩密集 | ✅ 好 |
| **独库公路** | 单线 | 不闭合、季节性封路 | ✅ 好（只有一条路） |
| **318 川藏南线** | 单线 | 超长（2100km）、海拔跨度大（500–5000m） | ⚠️ 无人区段更多 |

**建议先做川西小环线**：结构最接近（都是环线），能最快验证"换数据不换引擎"。
**但更该做 318**：它是**结构不同**（单线不闭合）+ **数据更难**的组合，能一箭双雕地压测抽象。
→ 我倾向 **先川西小环线（快，验证基本复用）→ 再 318（狠，验证边界）**。

### 6.2 验收标准（可量化，避免自欺）

| # | 指标 | 目标 |
| ---- | ---- | ---- |
| A1 | 引擎改动量 | 加第二条线，`engine/` 改动 **0 行** |
| A2 | 数据文件 | 只新增 2 个文件（`route-defs/xxx.js` + `.data.js`） |
| A3 | 构建时长 | 单条线全量构建 **< 5 分钟**（青甘实测 2分11秒） |
| A4 | 第一屏可用时间 | 打开页面到路线出现 **< 2 秒**（含按需加载） |
| A5 | 回归测试 | `c4-test.js` 从"测青甘"改为"**对任意线路包跑**"，全绿 |
| A6 | 新线体检 | V1–V4 全部通过，或有明确标注 |

**A5 是最有说服力的一条**：测试能从"这个页面是对的"变成"**任何线路包进来都是对的**"，才算平台。

## 7. 执行顺序（这份规划的核心交付）

### 原则

1. **每步都能独立验收、独立上线**，不做"半年憋大招"
2. **先做最难的验证**，不做最舒服的部分
3. **青甘线全程保持可跑**，不做破坏性重构

### 阶段表

| 阶段 | 内容 | 为什么这个顺序 | 验收 |
| ---- | ---- | ---- | ---- |
| **S0** ✅ | **缩放分级**（遗留问题） | 不是平台的事，但**它证明了引擎必须输出分层数据** —— 这是抽象的入口。先做，因为小、独立、立刻可见 | 远景只显示关键站；中景加弱化站；近景全显 —— **已达标，见下方实测表** |
| **S1** | **线路包契约落地**：把青甘数据抽成 `route-defs/qinghai-gansu.js`，页面改读它 | 只搬数据不改行为，**零风险**，但立刻暴露"契约有没有漏字段" | 页面行为与现在**逐像素一致**；c4-test 全绿 |
| **S2** | **契合器**：`engine/` 消掉所有青甘硬编码（含 `buildDays` 的专属分支） | 骨架通用化。**S1 的契约在这一步被真实使用** | `engine/` 里 grep 不到任何青甘地名/里程 |
| **S3** | **构建管线参数化**：`build-route.js <线路包>` / `build-stations.js <线路包>` | 让"加线"从手工变脚本 | 用青甘包重跑，产出与现有数据**一致** |
| **S4** | **体检 + 可信度透出**（§5） | 有第二条线之前必须建好，否则新线的错数据无人发现 | V1–V4 全绿；长盲区在页面上可见 |
| **S5** | **页面内编辑模式**（§3.3） | 让用户能自己改文案 —— 这是"不依赖我"的关键 | 改天标题/天数/地名，刷新后保留，可导出 |
| **S6** | **第二条线：川西小环线** | **验证抽象**。做不到零改动就回来修 S2 | A1–A6 全达标 |
| **S7** | **第三条线：318 川藏南线** | 压测边界（单线不闭合 + 海拔跨度大 + 无人区更多） | 同上，且引擎改动仍为 0 |
| **S8** | **多线路入口**（选线器 + 按需加载） | 有了 2–3 条线，才需要入口 | 打开页面选线，各自独立加载 |

### 为什么 S0 在 S1 前面

你可能觉得"缩放分级"和平台化没关系。**关系很大**：

现在所有站点平铺在图上（100 个标记叠着），根本原因是**引擎不知道"哪些站重要"**。
而"哪些站重要"取决于**车（续航）+ 路线（缺口）+ 当前视口** —— 这是**跨数据源的派生信息**。

**这正是"引擎要输出分层数据"的第一个真实案例。**
先做它，S2 的抽象才有具体的形状可以依；先做 S2 再做 S0，会返工。

### S0 完成记录（2026-09-25/26，实测非估算）

**第一版设想被实测推翻。** 我原本打算"按 zoom 分三档（远/中/近景）显示不同图层"，
先在 Node 里把 `dedupeByScreen` 单跑了一遍，发现**同一套屏幕去重算法在不同 zoom 下天然就能自动稀疏**：

```
z=5.5 → 70 点 ｜ z=7.3 → 178 点 ｜ z=11 → 332 点
```

所以"缺分级"这个判断本身是错的。**真因是旧代码把去重按死在固定 `z=7.3` 上算了一次**，
全览和近景看到的点一样多 —— 不是没有分级，是分级被写死成了一个常数。

**最终实现（两段式选点）**

1. **覆盖率代表点**：按 **60km 里程网格**挑最贴路的站，**直接入选，不参与像素去重**
2. **其余站走像素去重**，权重 `必充站 10 > 锚点 5 > 普通站 1`，同像素相撞保留权重高的
3. **合并**：锚点之间不判重；普通站落在锚点 6px 内则丢弃

去重阈值随 zoom **连续插值**（40px → 18px，区间 z=6~10），不用阶梯 —— 避免缩放时"突然冒出一堆点"的跳变。

**实测结果（1600×900 全览 z≈7.3）**

| zoom | 分级 | 阈值px | 加油站层 | 充电站点 | 加油站点 | 地图合计 |
| ---- | ---- | ---- | ---- | ---- | ---- | ---- |
| 5.5 | far | 40 | **隐藏** | 36 | 43 | **36** |
| 6 | far | 40 | 隐藏 | 40 | 48 | 40 |
| 7 | mid | 34.5 | 显示 | 53 | 67 | 120 |
| 7.3 | mid | 32.9 | 显示 | 60 | 72 | **132**（修复前 178） |
| 9 | near | 23.5 | 显示 | 107 | 109 | 216 |
| 11 | near | 18 | 显示 | 150 | 139 | 289 |

**两条只有实测才能暴露的教训（已写进防回归断言）**

- **显示层不得放大数据缺陷**。纯按像素去重时 z=5.5 只剩 12 个点，站间空档 **554km**，
  而全量真实数据只有 **199.9km** —— 显示层凭空造了 354km 的"假无人区"。
  修好后：显示层 z=5.5 的站间最大空档 = **199.9km**，与真实数据 **1:1 还原**。
  （根因：锚点被一起送进去重，40px 阈值在 z=5.5 时约等于 120km 实地距离，把 60km 一个的锚点自己吃掉了）
- **修掉一个数据自相矛盾的既有 bug**。页面里长期同时存在两套站点图层：
  旧的 `fuelMarkers`/`evMarkers`（手打的 `FUELS`/`EVS` 各 12–13 个示例站）
  与新的 `dimFuelM`/`dimEvM`（真实 `STATION_DATA`，282 充电 + 193 加油）。
  两套叠着画 169+ 个点，且**坐标不一致 → 同一个加油站在图上出现两个位置**。已删除旧图层。

**这一步对平台化的意义**：证实了"哪些站重要"是 **`车续航 × 路线缺口 × 当前视口` 的跨数据源派生信息**，
引擎必须把"分层后的站点"作为一等输出物 —— 这就是 S2 抽象的形状。

### 时间不是重点，顺序才是

这份规划不写工时估计 —— 估了也不准，而且会让你误以为"在按计划推进"。
**你只需要看阶段顺序对不对，以及每阶段的验收标准合不合你的意。**

## 8. 风险与不做的事

| 风险 | 我的判断 |
| ---- | ---- |
| 抽象过度，做成谁都用不顺的框架 | §2.1 已划边界：支持主折线+分段+支线，不支持路网。S6/S7 是刹车 |
| 每条新线的途经点/分段仍需人工 | §3.2 分工原则：几何必须人定（这是产品判断），但**从"我手打"变成"页面里改"**，用户可自助 |
| 站点数据在腾讯下抓不全 | 不解决，只**诚实表达**（§5.3）。换高德能改善但拿不到枪数（已实测） |
| 单文件变多文件后回不到"刷一下就看" | §4.3：不引入构建工具链，保持改文件刷页面 |
| 数据量膨胀 | §4.3 按需加载 |
| 平台化后每条线的文案质量下滑 | 模板生成骨架 + 用户改；**不假装文案是自动的好文案** |

### 明确不做（这一轮）

- ❌ 枪数（已实测：腾讯/高德开放 API 都没有，运营商裸接口打不通）
- ❌ 实时路况 / 天气
- ❌ 多线路串联（"青甘+川西连走"）
- ❌ 路网自由规划
- ❌ 用户账号 / 云端存储（编辑结果先存本地 + 导出）
